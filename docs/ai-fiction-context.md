# 用《门后的火光》理解 Context Engineering

对应无统一计时的实验墓室规则 v4、正式冒险规则 v6。目标：看懂开局、每轮裁定、复核和重裁的真实数据流，能区分“模型知道什么”“玩家知道什么”“程序允许改变什么”。本文依据本仓库代码；API 概念参考 OpenAI 官方 Conversation state 与 Structured outputs 文档。

## 1. 开局没有模型调用

POST /api/fiction-lab，body 为 {"op":"start"}。服务创建实体、地点、机关与预写开场，分配会话并存进 D1，再返回页面使用的 game。没有让 LLM 临场生成剧本。GET 恢复存档、相同 requestId 的已完成重试也不重新调用模型。

原始 PDF、我们在聊天里对项目的讨论、你的其他对话、网页截图，不会自动出现在游戏主持的上下文里。当前不使用向量数据库、自动读文件、联网搜索或工具调用；历史检索在应用内按实体、记忆类型、词语与轮次完成。

## 2. 每次行动，应用重新组装上下文

```text
玩家输入
  → 服务读取 D1 存档
  → 调用 A：裁定（结构化提案）
  → 程序在副本中检查并结算
  → 调用 B：复核与叙述
  → 通过：状态与幂等回执一起保存 → 页面显示正文
  → 不通过：带原因，从本轮原始存档最多重裁一次
```

两次正常调用使用同一个 gpt-5.6-sol，但职责与输入不同；不是两个常驻、共享记忆的模型。请求设置 store:false，没有 previous_response_id/conversation 串联，没有重放推理项。跨轮记忆由应用存档与本次明确发送的资料提供，不表示模型记住整段历史。store:false 也不能替代上游服务的数据保留政策。

## 3. 调用 A 收到什么

API 请求有两条消息，以及独立的输出格式约束：

```js
{
  model: "gpt-5.6-sol",
  store: false,
  stream: false,
  reasoning: { effort: "low" },
  max_output_tokens: 4200,
  input: [
    { role: "developer", content: HOST },
    { role: "user", content: JSON.stringify({ world, player_action }) }
  ],
  text: { format: proposalFormat }
}
```

| 部分 | 本项目实际内容 | 为什么发送 |
| --- | --- | --- |
| developer / HOST | 主持职责、常识裁定、连续动作与暂停规则、位置边界、无倒计时、输出字段含义、禁止擅改规则 | 确定裁定方式，不让玩家原话覆盖游戏规则 |
| world.places | 三处地点及空间关系 | 区分身处、能看见、能投到的位置 |
| world.entities | 全部已有实体的身份、普通物性、位置、完整性、最新事实、材料来源等 | 保存布已湿、物品已投出等跨轮后果 |
| world.knownEntities | 玩家上次看见的物品位置与事实 | 后台可以知道关门后的燃烧结果，正文不能全知泄露 |
| 当前状态 | 位置、状态值、门开闭、悬锤是否已落、rulesVersion/mode | 稳定关键设定；明确旧倒计时已经废止 |
| notes | 最近16条带 revision、来源与 historical 标记的观察 | 明确是当时所见，不能否定后来已经改变的状态 |
| memories | 最多12条相关记忆与有效约定/计划/命名，保留逐字来源、状态与知识归属 | 记住口头约定，不依赖故事中的纸质手记 |
| commitmentLedger | 最多16条约定/计划的最新状态、原话与兑现/取消来源；优先12条仍有效事项，并为已处理事项保留空间 | 离场时也能检查旧委托，避免仅靠当前输入的关键词检索；total/complete 明示覆盖范围 |
| history / retrieval | 从完整公开日志检索的最多6个旧轮次，保留玩家原话与当轮叙述、轮次、截断及覆盖提示 | 查询最初/后来位置与旧约定；明确检索不完整，不能据缺失断言从未发生 |
| recent | 最近6条玩家/叙述日志，不是6整轮 | 保留指代、语气和局部对话关系 |
| recentEvents | 最近3次程序接受的结构化结算 | 提供可靠的近期因果证据 |
| pendingDecision | 上次目的、原行动、暂停原因、问题、尚未执行的动作 | 理解“照样扔”“先不扔”这样的短接续 |
| player_action | 当前自由输入，或被选建议按钮的文字 | 本轮要解决的请求 |
| text.format | strict JSON Schema | 规定提案格式，方便程序检查；不保证物理与语义一定正确 |

world 作为 user 消息中的 JSON 资料发送，并不是额外系统指令。历史中的 role 字段也只是资料字段，没有被提升为本次 API 的 developer 消息。

当前场景很小，发送全部实体；旧对话按当前输入做有界相关性检索，实体快照本身不检索。完整日志不会整本发送，Cookie、token_hash、API Key、IP、数据库锁等不会放入 world。世界数据和已有日志来自玩家交互，因此 HOST 明确要求把其中的指令式文字当资料。

## 4. 调用 A 返回什么

以下是格式示意，字段完整但内容不是声称某次模型逐字输出：

```json
{
  "intent": "尝试点燃白垩，再投到门内",
  "steps": [{
    "attempt": "将白垩凑近油灯火焰",
    "status": "failed",
    "beat": "action",
    "requires_previous_success": false,
    "scope": "near",
    "refs": ["lamp", "chalk"],
    "move_to": "stay",
    "door": "unchanged",
    "end": "continue",
    "updates": [],
    "creates": [],
    "outcome": "白垩未能点燃，仍在手中，尚未投出。",
    "observations": []
  }],
  "decision": {
    "disposition": "replace",
    "needed": true,
    "question": "白垩没有燃起来，仍然投出吗？",
    "pending_action": "将白垩投到门内近处",
    "reason": "试火目的可能落空，继续投掷会失去手中物品。"
  },
  "evolution": { "basis": "none", "updates": [], "observations": [] },
  "memory_updates": []
}
```

steps 是待检查的提案：updates 修改已有实体，creates 只能从实际损失的材料派生碎片。beat 区分实际操作、明确等待、纯确认，没有数值耗时。decision 用 disposition 明确没有待选事项（none）、保留（keep）、新建或替换（replace）、执行解决（resolve）、明确取消（cancel）。追问不覆盖原话或清除旧事项；机关强制中断也保存未执行部分。decision 保存待决定事项；evolution 记录有实际行动或明确等待依据的自然变化，暂停时必须为空。

memory_updates 每轮最多4条：提取口头约定、计划、命名或已观察发现。新条目引用本轮玩家原话，或已执行步骤中逐字存在的观察；程序验证来源、类型与实体引用，分配稳定ID。修改有效状态另存本轮证据，保留原内容和原出处，不覆盖历史。引用校验不等于语义真实性证明，第二次调用仍须复核。记忆只是资料，不自动授权重要行为。玩家明确离场时，已委托且仍可行的低风险顺路琐事可由主持在本轮真正结算；履行必须引用已执行步骤的观察，不能引用玩家的计划当成完成证明。

随后程序验证位置邻接、物品来源、不能复活或无故修复、关键机关和暂停约束。在内存副本中结算；这时还没有写入正式存档。模型可能给出符合 JSON 格式却不合理的答案，格式约束不能替代这些检查。

## 5. 调用 B 收到与返回什么

第二次请求同样有 developer 和 user 两条消息，developer 换成 NARRATOR。user 包含：

- player_action：玩家原话；
- before：行动前的完整主持上下文；
- confirmed_steps：程序实际接受的步骤，可能已被机关或暂停截断；
- decision：待玩家决定的事项；
- evolution：已检查的持续变化；
- memory_changes：本轮候选新增或更新的记忆，逐条复核，不受检索数量上限影响；
- after：应用结果后的主持上下文；
- ending：是否真的结束。

输出上限2200 tokens，格式是：

```json
{
  "consistent": true,
  "issue": "",
  "issue_code": "none",
  "narration": "灯焰掠过白垩，它没有燃起来。你仍握着它，尚未投出……"
}
```

这个调用既复核“是否偷换意图、擅自行动、泄露不可见信息”，也负责写玩家看到的正文。它知道 before/after 两个世界快照，因此必须遵循玩家视野限制。复核也由模型完成，仍可能漏判；程序硬约束与语义复核各有边界。

## 6. 内部修正与真正保存

若程序拒绝提案或调用 B 判为矛盾，下一次调用 A 收到同一份原始 world、同一 player_action，额外带 correction：上一份未提交提案和具体拒绝原因。不能从错误候选继续推进。

最多修正一次：正常2次模型调用，失败路径最多4次，共用90秒裁定截止；预算或网络错误不当作语义问题无限重试。全部通过后才原子保存状态与 requestId 回执，避免玩家点重试而重复丢物或重复触发机关。

常规游玩接口只返回 game 投影：正文、背包、已知线索、地图、建议、待决定事项等。新增的“主持调用详情”是独立学习入口：主动展开后，会经本局 Cookie 验证读取真实请求，其中包含主持完整世界，因此界面标明可能剧透。它不改变普通正文的视野规则。

## 7. 本项目中值得学习的四个设计选择

1. **记忆分层。** entities 保存当前事实，knownEntities 保存玩家知识，recent 保留短期对话，pendingDecision 保存未完成意图。关门后看不见火势、补答能认出白垩，靠的是不同记忆层。
2. **信息优先级。** 稳定规则在 developer，世界和玩家文字是资料。旧日志里的灯油期限需要被明确的新规则覆盖。
3. **事实与文字分工。** 先提案、校验，再叙述，最后提交；漂亮的故事文字不能直接变成有效存档。
4. **上下文有取舍。** 最近6条日志用于短期衔接；重要约定另存记忆账本，旧日志按需检索。上下文最多12条记忆、6个旧轮次（每条原文最多1800字符），不等于全部历史。完整日志、记忆变更、带轮次观察及新版事件在存档追加保留，查询时才选择；当前仍是18实体的小场景，也未验证数百轮存档容量或多章节召回。before/after重复发送有成本，当前优先易于复核。

源码：functions/_lib/fiction-lab-host.js（两套提示词、两个schema、修正循环）；fiction-lab-engine.js（hostContext与状态结算）；fiction-lab-memory.js（来源校验、记忆账本、旧日志检索）；fiction-service.js（API请求、预算、存档事务）；functions/api/fiction-lab.js（组装入口）。

## 8. 在网页检查真实上下文

试玩右侧手记下方的“主持调用详情”默认收起，手机上随页面排列。展开可选本局某次行动，按调用顺序查看裁定、复核及内部修正；每次调用提供 developer 规则、解开 JSON 字符串后排版的 user 资料、模型参数与 schema、完整请求 JSON、返回内容及原始返回文字。宽屏阅读使用可按 Esc 关闭的对话框，也可下载本次 JSON。

记录从功能上线后的行动开始，开局没有调用，旧轮次不补造。它记录发送给 API 的实际请求正文，以及应用收到的 output_text 与输入/输出 token 数；不记录授权头、密钥、Cookie、上游地址、原始错误正文或模型内部推理。网络失败没有返回内容时明确显示缺失，不以故事摘要代替。token 数与耗时来自实际响应/测量，没有额外发起模型请求。

每次行动尝试的调用记录独立存于 koa_fiction_traces，保留 7 天，按 Cookie 对应的 session_id 限定读取；重新开局不再通过新存档查看旧局。列表每次20条，可继续加载更早记录。成功提交、失败未提交与内部修正分开标注，幂等回执重放不制造新调用。学习记录不进入 game 状态或 hostContext，不形成逐轮重复膨胀的模型记忆。

读取详情使用独立请求配额；收起时不请求详情。记录写入失败不回滚已成功保存的游戏，这种情况下该次记录可能缺失。新增表随接口初始化创建，不重写剧情存档。

## 9. 冒险名字不进入主持上下文

命名收藏保存的是服务端已经提交的玩家视图快照：完整正文、结局、背包与已知记录。它与用于继续游戏的自动进度、用于学习的调用记录是三份独立资料。收藏标题不修改剧本、世界实体或近期对话，也不调用模型重写故事；改名与导出同样不调用 LLM。

收藏不随当前进度的七天期限删除，依赖本浏览器的独立收藏凭证访问。可以导出单文件 HTML 离线阅读与 JSON 留存；此版收藏只供重读，不支持从快照恢复游玩。

## 8. 2026-09-20 长程测试后的字段约定

- `place=carried` 表示手持或随身；房间ID表示留在房间。拿起、收好不能只改自然语言facts。
- `status/ending` 决定是否结束；`location` 可以保留最后地图位置，公开界面标成“最后所在”。
- `evolution` 只处理主动步骤之外的持续变化。主动移动已结算时，`basis=none` 也合法。
- 正文按信息量写：复杂操作和重要发现仍允许300—440字，简单动作80—180字，询问确认40—120字，避免未变物品清单。
- 旧v3存档按 `memoryVersion=1` 惰性补齐记忆结构，读取不写数据库，下一次成功行动才原子保存；已有原文可检索，但不会伪造已被旧版裁掉的结构化事件或不确定的观察轮次。
- 历史观察不是当前状态。模型记忆中的玩家声明也不是已执行事实；隐藏的后台演化不进入公开日志检索或自动变成玩家发现。

## 11. 2026-09-21 有人情味的主持裁量

`fiction-discretion.js` 给裁定与复核发送同一份规则，避免裁定允许通融、复核又机械否决。新规则仍放在每次调用的 developer 消息中，不单独增加模型调用。

- 求助先给可见或已知线索及用途，重复求助给具体下一步；明确要解法时可以解释当前操作。提示不代执行、不消耗资源、不推进危险，也不按性别区别待遇。
- 普通障碍允许合理便利和效果等价的方法；重要资源、交易、牺牲、危险和核心真相保持约束。
- 已委托的顺路小事在离场时可以补完，必须先写入 steps、实体归属与观察，再叙述尾声。结算记录保留 `end` 与移动等字段供复核。
- `commitmentLedger` 始终按确定性规则从现有记忆账本计算；无需模型摘要，也不增加存档表。它不是完整任务清单，未曾提取为记忆的约定仍依靠原文检索，超过容量也明确标记不完整。
- 程序确保 fulfilled 的来源是实际步骤中的逐字观察；语义上是否确实兑现，仍需要模型复核。这不等于所有自然语言资源和事实已有硬校验。

真实模型回归入口与评分标准见 [主持裁量验证](fiction-discretion.md)。
